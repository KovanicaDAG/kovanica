## 1. Purpose & Regulatory Basis

This policy governs the integration, configuration, and ongoing management of **Sumsub** as the outsourced KYC/CDD provider for Kovanica Protocol d.o.o. ("the CASP") under MiCA.

| Regulation | Reference |
|------------|-----------|
| MiCA | Articles 16–17 (fit & proper, governance), Article 30–31 (outsourcing) |
| AMLD6 / Croatian AML Act | Articles 13–18 (CDD), Article 28 (outsourcing) |
| EBA Guidelines | EBA/GL/2019/02 (outsourcing), EBA/GL/2022/01 (ML/TF risk factors) |
| GDPR | Articles 28 (processor), 32 (security), 44–49 (transfers) |
| DORA | Articles 28–30 (ICT third-party risk) |

**Classification:** Sumsub is a **critical outsourced function** (KYC/CDD) per MiCA Art. 30 and DORA Art. 28.

## 2. KYC Tier Configuration

Aligned with `00_AML_Policy.md` risk ratings:

| Tier | Risk Level | Sumsub Level | Checks Included | Trigger |
|------|------------|--------------|-----------------|---------|
| **Tier 1** | Low | Basic | Email, Phone, Liveness, Document (ID/Passport), Document authenticity | Natural persons, low-value (< €1,000), domestic |
| **Tier 2** | Standard | Enhanced | Tier 1 + Proof of Address (utility bill, bank statement ≤ 3 months), Source of Funds declaration | Standard onboarding, EU residents, transaction volume €1k–10k/month |
| **Tier 3** | High | Full EDD | Tier 2 + Source of Wealth documentation, Adverse Media screening, PEP/RCA screening, Ongoing monitoring (continuous) | High-risk jurisdictions, PEPs, complex structures, > €10k/month, crypto-native businesses |

**Escalation:** Any Tier 1/2 client triggering enhanced risk factors (sanctions hit, adverse media, unusual activity) auto-escalates to Tier 3.

## 4. Data Flow Architecture

```text
┌─────────────┐     ┌──────────────┐     ┌─────────────┐     ┌──────────────────┐
│   Client    │────▶│   Sumsub     │────▶│  Webhook    │────▶│  Internal KYC    │
│  (Browser/  │     │  (KYC/CDD)   │     │  Receiver   │     │  Decision Engine │
│   Mobile)   │     │              │     │             │     │                  │
└─────────────┘     └──────────────┘     └─────────────┘     └────────┬─────────┘
                                                                       │
                                                                       ▼
                                                            ┌──────────────────┐
                                                            │  Client Notify   │
                                                            │  (Approve/Reject/│
                                                            │   Request More)  │
                                                            └──────────────────┘
```

### 4.1 Step-by-Step Flow

1. **Client Initiation** — Frontend loads Sumsub Web SDK with `accessToken` (short-lived, generated by backend)
2. **Data Collection** — Client completes liveness, document upload, address proof, source of funds/wealth forms
3. **Sumsub Processing** — Automated checks (document authenticity, face match, liveness, database checks)
4. **Webhook Notification** — Sumsub POSTs to `webhookUrl` with `applicantReviewed` (or other event)
5. **Internal Decision** — KYC Decision Engine evaluates:
   - Sumsub result (`approved` / `rejected` / `onHold`)
   - Risk tier alignment (Tier 1/2/3 checks completed)
   - Sanctions/PEP screening results (Sumsub + internal)
   - Blockchain analytics risk score (if applicable)
6. **Client Notification** — Backend updates client status, triggers in-app/email notification
7. **Record Creation** — KYC record stored with Sumsub `applicantId`, decision, reviewer, timestamp

## 8. Fallback Procedures

| Scenario | Detection | Response | SLA |
|----------|-----------|----------|-----|
| **Sumsub API Downtime** | Health check failure (3 consecutive 5xx) | Activate manual review queue; clients directed to "upload documents manually" flow | < 15 min detection, < 1h manual queue active |
| **Webhook Delivery Failure** | No 2xx response after 3 retries (exponential backoff: 1m, 5m, 15m) | Alert on-call; manual poll `GET /applicants/{id}` every 5 min | < 5 min alert |
| **SDK Load Failure** | Frontend error boundary catches SDK init error | Fallback to "manual document upload" form; log error to Sentry | Immediate |
| **Data Discrepancy** | Sumsub `GREEN` but internal sanctions hit / adverse media | Auto-escalate to Tier 3 manual review; audit trail recorded | < 30 min |
| **Sumsub Data Breach** | Sumsub notification or public disclosure | Activate Incident Response Plan (see `06_Incident_Response_Plan.md`); assess data impact; notify DPA (72h), HANFA (if material) | Per IRP |

**Circuit Breaker:** After 10 consecutive webhook failures, circuit opens for 10 minutes; manual polling continues.

## Appendix A: Sumsub Applicant Lifecycle States

| State | Description | Next Actions |
|-------|-------------|--------------|
| `pending` | Applicant created, checks in progress | Wait for webhook |
| `prechecked` | Pre-check passed, awaiting full review | Auto-advance or manual trigger |
| `onHold` | Manual review required | Compliance team reviews |
| `approved` | All checks passed | Activate account |
| `rejected` | Checks failed | Notify client, log reason |
| `expired` | Applicant not completed in 30 days | Archive, allow re-application |

## Appendix B: Webhook Signature Verification (Pseudo-code)

```python
import hmac
import hashlib
import base64

def verify_webhook(payload: bytes, signature_header: str, secret: str) -> bool:
    """
    Sumsub signs with HMAC-SHA256, base64-encoded.
    Header format: 'sha256=<base64_signature>'
    """
    expected = base64.b64encode(
        hmac.new(secret.encode(), payload, hashlib.sha256).digest()
    ).decode()
    received = signature_header.replace('sha256=', '')
    return hmac.compare_digest(expected, received)
```
